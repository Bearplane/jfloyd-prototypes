Why Q-Audit, not Q-Config

  • Audience. Q-Config is what a processor (and merchant) configures for their own tenancy — Sources → Features → Plans, invite configuration, scanner settings. A merge is Qredible acting on someone else's records. That is a super-admin operation, and Q-Audit is the only surface already role-gated to SuperAdmin.
  • The data is already here. The Companies table, company summary view (Summary · Locations · Products · Monitor · Billing · RTQ) and the Activity Log all live on this page. The wizard pulls from and writes to exactly these.
  • Blast radius. Q-Config renders inside tenant-facing navigation; putting a destructive cross-tenant tool there invites accidental exposure via a plan/feature toggle. Q-Audit is never entitlement-driven.
  • Not merchant self-service, not a notification. Merchants never see a "merge" control. The only merchant-visible artefact is the ownership-proof request they complete (screen 2).

Who does what

Merchantcompletes the ownership-proof request when Qredible sends it (uploads / attests). Nothing else.
Qredible ops (SuperAdmin)reviews the proof → Approve / Reject. Approval unlocks "Merge duplicate company…".
Qredible ops (SuperAdmin)runs the wizard: records → survivor → decisions → preview → confirm.
Systemapplies in one transaction, journals every row, writes the ledger + audit, can reverse for 30 days.
Initiated by us, always. There is no merchant-side "merge" button and no notification the merchant has to act on to trigger a merge. The processor (e.g. the referring ISO) also cannot initiate — they can only tell us.

Ownership proof — the gate in front of the merge

Before a merge can even be initialised, Qredible must be satisfied that the person on the surviving login truly is the company that owns the other record's data. This is a manual, admin-reviewed step with its own record (pl_company_ownership_proof). The merge row action stays disabled until a proof for this pair is APPROVED.

Reversibility is a property of the journal, not of the wizard. Reverse replays the items in reverse order in one transaction (re-point back, re-insert collapsed rows from their snapshots, restore field values, un-archive). It refuses if the survivor has gained rows since the merge whose ancestry is ambiguous (e.g. new products) — the operator can override ("reverse anyway, new rows stay on the survivor"). Post-commit side effects that were irreversible (a gateway cancellation) are listed as manual.

Failure — what happens when it can't complete

Four distinct failure points, each with a different guarantee. The design rule: the database is never left half-merged; the only things that can be "partial" are post-commit side effects, and those are idempotent and retryable.

① Planner refusesa guard is red · nothing written · merge row stays PLANNED with the reason
② Apply throws mid-waytransaction rolls back · DB identical to before · merge row → FAILED with error + phase
③ Post-commit side effect failsDB is merged (APPLIED) · warning recorded · "Retry side effects" button · safe to repeat
④ Reverse failsreverse is its own transaction · rolls back to APPLIED · nothing half-reversed

Why re-plan and not retry: the stored plan was computed against the data as it was. Anything that changed since (a new MID, a scan that started, a new product) can make it wrong, so a failed apply always goes back through the gate check. Retrying the identical plan is never offered.

What makes ② safe

  • One queryRunner transaction for phases 1–7; SELECT … FOR UPDATE on both company rows first.
  • The journal is written inside the same transaction, so a rollback also discards the journal — no orphan "undo" lines.
  • Post-commit work (phase 8) is queued from the commit callback, not run inside the transaction — a slow cache cannot hold row locks.
  • Unique-key collisions are pre-computed in the plan; a collision that appears between plan and apply is exactly case ② and surfaces as a clear error, not a half-merge.
Human failure is handled by the same machinery: "we merged the wrong pair" is a Reverse within 30 days (screen 7). "We merged the right pair but chose the wrong survivor" is Reverse, then a new merge in the other direction — the ownership proof is still valid for the pair.
