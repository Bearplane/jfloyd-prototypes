Bundle vs Kit, resolved from Q-Transact's code: commerce-mechanically identical (same member table, both explode into member order lines, neither separately stocked). The real difference is assembly/labeling — a Kit composes member labels into one artwork and can't publish until every member is published & labeled. That maps 1:1 onto COAs: members individually labeled → aggregate their COAs (Bundle); assembled into one labeled unit → it plausibly has its own combined COA (Kit → Individual default). Defaults, not rules — the level stays selectable.

Why a product type — and why not a classification (Rev 2 grounding)

Classification's job is per-item compliance determination: the category tree is family → classification (self-hierarchical), each classification carries a COA-requirement, and classification effectively propagates to children. A bundle is the same concept in every family and links items rather than describing what an item is — a "bundle" classification would both fail to map (one per family?) and wrongly stamp bundle-ness onto every member. So bundle lives on a new structural axis: product type, leaving family/classification free to drive compliance for each bundle member individually.

Rev 1 proposed a bare is_bundle flag; rev 2 upgrades it to the full taxonomy because Q-Trust also needs the container distinction (which a bundle-only flag can't carry) and because Joseph wants consistency with Q-Transact.

The taxonomy, read from Q-Transact's code — not invented

  • Persisted enum is exactly SIMPLE | VARIABLE | BUNDLE (default SIMPLE). There is no persisted KIT: Kit = BUNDLE + is_kit=1, inflated to a fourth choice in the admin UI and deflated on save. Q-Trust mirrors this contract literally — same words, same storage trick — so the two products can never drift apart on vocabulary, and a future catalog crosswalk is the identity function.
  • Bundle vs Kit, answered: mechanically identical (same member table, both explode into member order lines, neither separately stocked). A Kit differs only in assembly: member labels composed into one artwork, a combined mockup, and a stricter publish gate. Compliance mapping: Bundle → members individually labeled → aggregate their COAs; Kit → one labeled unit → own combined COA by default. Defaults, not rules.
  • Variable = the explicit container flag Joseph asked for. Today container-ness is only inferred from COA levels (a level-Child parent, or children at level Parent). Rev 2: type Variable marks the container; the level keeps expressing which COA topology the family uses — children-hold-COAs (Child) or container-holds-the-family-COA (Individual + children at Parent). A parent that is itself a real product stays Simple. Backfill converts the two unambiguous patterns by script and routes the ambiguous tail to Tidy Up suggestions.
  • Linking model kept (Joseph's point 3): members are existing catalog products, stored in pl_product_bundle(main_product_id, include_product_id, quantity, sort_order) — Q-Transact's table shape plus quantity. Members must pre-exist (or be created inline as normal catalog rows); only Simple/Variable can be members — no nesting, same as Q-Transact's picker. Member standalone rows are untouched.

COAs and counts (carried from rev 1, unchanged in substance)

The row carrying the Bundle assignment level is an aggregate of its members' effective statuses — the shipped variant-parent roll-up applied to the member set, with worst-of disposition, dashed derived chips, and expand-to-members as the audit affordance. Members that are themselves Shared/Inherited/Parent resolve through the existing owner chain. No double counting: members count individually; the level-Bundle row stays outside the counted universe; a Kit at level Individual counts as a normal COA owner. The KPI partition invariant is untouched; one informational "incl. N bundles" split is added. Fixed for free: today's silent lie where a level-Bundle product reads Compliant even with a violative member.

Auto-establish at ingestion — the feasibility answer

Partially automatable now; deterministically automatable after one contract change. The scan pipeline is entirely platform-agnostic — the spider normalizes every site into one product shape and discards platform product types and component lists before Middleware sees them; parent/child is built only from explicit variant data (precise, zero discovery); the only surviving signal for bundles is the title string. Hence the staged plan: (I-1, buildable now) stamp Variable automatically wherever explicit variant data exists — near-perfect; detect bundles from title tokens + ≥2 catalog-member matches and surface them as suggestions through the existing engine (new BUNDLE_COMPOSITION group, reserved SCAN_AUTO_INGEST producer, no migration) — never auto-applied from heuristics. (I-0, the real unlock) widen the spider contract to carry platform types, component lists, and structured variant axes; then type mapping is deterministic and earns auto-apply with the reserved AUTO_APPLIED_AT_INGEST audit stamp. One collision handled deliberately: bare "pack/ct/count" titles stay weight/size variants (the existing regex already claims them); multi-count of the same product is a variant, composition of different products is a bundle.

Open decisions

  • Quantity in v1? Column + one input, ignored by COA logic (Q-Transact has none; ours is a superset). Recommend yes.
  • Adopt is_kit in v1 or ship Bundle-only first? Recommend adopt — one tinyint, settles the taxonomy permanently.
  • Container backfill aggressiveness — script the unambiguous, suggest the rest. Confirm.
  • Member archive semantics — exclude-with-note (recommended) vs block.
  • I-0 ownership — the spider contract lives outside these repos; needs the spider owners before that ticket is fileable.
  • Pack-token blast radius — leave the shared weight/size regex untouched in v1; the bundle detector overrides per-row on confirmed member evidence.

Build sequence (ticket-shaped)

  • B-1 API — type taxonomy + membership schema: product_type + is_kit + source_product_type columns, pl_product_bundle table, invariants + convertibility, container backfill + suggestion sweep, upsert DTO/handlers, healing script for stray level-Bundle rows.
  • B-2 API — aggregate status + statistic split: Bundle roll-up branch, worst-of disposition, bundle counts (coordinate the pending parent-split statistic work), export-text drive-by fix.
  • B-3 UI — create/edit with type picker: four-way type selector (Kit inflate/deflate), Variable/Bundle modal modes, member picker + create-for-bundle, level constraints per type, bundles_01 gate.
  • B-4 UI — table rendering: Bundle/Kit pills, member expansion, aggregate chips, container affix, optional Type column, KPI sub-label, "Bundles only" facet.
  • B-5 MW — ingest (I-1): Variable auto-stamp, bundle detector + BUNDLE_COMPOSITION suggestions, bundleIngest_01 gate.
  • B-6 cross-team — spider contract (I-0): platform types, component lists, structured variant axes; deterministic mapping + auto-apply stamp.
  • B-7 follow-ons: "In N bundles" badge, at-risk KPI, family-tree second edge type, strain/weight two-level enablement, Transact crosswalk.
