Why a bundle flag, not a new product type taxonomy (and not the classification)

Grounding correction first: there is no "bundle" classification in code. Classification in Q-Trust is a data-driven category list (pl_category rows); no category named Bundle exists in code or seed SQL. The only BUNDLE in the codebase is the COA Assignment Level value — declared, labeled ("Bundle — derives status from component products"), stored in MySQL since release 3.20, and explicitly marked NOT wired in the API: the component relation was left as an open decision, so a Bundle-level product today renders a permanent "Missing (0)" placeholder and silently reads Compliant in the KPIs. The product type column is a free-text cosmetic field (Broad/Full Spectrum) and can't carry structure.

Joseph's instinct — that COA level alone can't drive bundle logic — is confirmed by three code facts: (1) the requires-COA invariant coerces levels on every write, so a non-cannabis gift set would lose Bundle-ness on save; (2) the level is freely mutable from three surfaces, and composition rows must not be conjured or orphaned by a dropdown; (3) display and parent/child logic need identity independent of COA state. But a full new type taxonomy is more than the job needs. The smallest change that works, matching codebase idiom (is_cannabis, is_archived):

  • pl_product.is_bundle — structural identity flag, set at creation. Invariants: a bundle has no parent and is nobody's child; level BUNDLE becomes settable only on bundles (one-time healing script normalizes stray rows).
  • pl_product_bundle_component — N:M join table (bundle, component, quantity, sort order; unique pair). A component may sit in many bundles; bundles-of-bundles are forbidden in v1, keeping aggregation single-hop like single-level parent/child.
  • The BUNDLE assignment level keeps its exact published meaning and finally works: default for bundles requiring a COA, aggregate computed by a sibling branch to the shipped CHILD roll-up.

Composition — Joseph's (a) and (b)

(a) Pick from catalog: search-first multi-select autocomplete (no full-catalog fetch), rich options with photo/SKU/COA chip, excluding self and other bundle rows. (b) Create for the bundle: "+ New product" opens the standard add-product form; the result is auto-linked as a component and remains a normal catalog row — that standalone row is exactly where its COA gets uploaded and managed. No shadow products, no hiding; provenance stamped via the created-source framework. Catalog products keep their standalone rows untouched while belonging to bundles.

COAs for the bundle — validating the aggregate model

Joseph's model holds: the row with the Bundle assignment level is an aggregate of its members. Each member contributes its effective status (Shared/Inherited/Parent members resolve through the existing owner chain — reused, never re-implemented). Fold rules: none-require → Not Required; any missing/unresolvable → Missing surfaces; else representative status. Disposition is worst-of. Rendered with the platform's existing derived vocabulary — dashed chips, ⤵, per-status counts, tooltip — and audited via expand-to-components. And the bundle can carry its own COA: set level Individual on the bundle (kit-level combined COA); identity and COA behavior are decoupled, so no new resolution semantics were invented.

Least disruption, tallied

New: one column, one table, one DTO field, one roll-up branch beside an existing template, one informational statistic split, one modal section, one expansion branch, one pill. Untouched: the assignment-level enum (no new members), chain-walking constants, the KPI partition invariant, parent/child relations, member standalone rows, the COAs tab, every existing chip and column. Fixed for free: the Bundle "Missing (0)" placeholder and its silent Compliant fold.

Open decisions

  • Quantity in v1? Column + one input, ignored by COA logic. Recommend yes (Transact/EDR will want it).
  • Seed a "Bundle" category? Recommend no — the flag backs an unambiguous "Bundles only" facet instead, avoiding the level/category naming collision.
  • Non-cannabis bundles? Supported (level Not Required). Confirm desired.
  • Archiving a component in an active bundle — v1 excludes it from the aggregate with a muted note (vs. blocking). Confirm.
  • "Bundles at risk" KPI sub-line — recommend fast-follow once real data exists.

Build sequence (ticket-shaped)

  • B-1 API — identity + composition schema: flag, join table, invariants, upsert DTO/handlers, healing script, listing RO fields.
  • B-2 API — aggregate status + statistic split: Bundle roll-up branch, disposition worst-of, bundle counts (coordinate with the pending parent-split statistic work), export-text drive-by fix.
  • B-3 UI — create/edit bundle: Actions ▾ entry, modal bundle mode, component picker + create-for-bundle, level constraints, dark-launch gate.
  • B-4 UI — table rendering: Bundle pill, expansion, component sub-rows, aggregate chips, KPI sub-label, "Bundles only" facet.
  • B-5 Follow-ons: "In N bundles" badge, at-risk KPI, family-tree edge type, quantity consumption downstream.

Everything downstream of B-1 keys off the identity-flag decision — it is the only true fork in the design.
