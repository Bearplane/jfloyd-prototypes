Full design explanation — the two questions this design answers

Ticket QP-4352 · Epic QP-4321 · Status: design for sign-off (product & engineering leadership). Everything below is grounded in engine behavior that is already built and tested — nothing here invents behavior.

Q1 — Does today's "one rule set" model change?

Yes — it generalizes, and the generalization is the same pattern repeated. Today there is exactly one rule set (the COA Validity Rules): a Qredible-managed global default, an optional per-processor override, and the merge of the two is the one effective set everything uses. Going forward, that same three-layer pattern applies once per policy instead of once globally.

A Policy is one authority's rule set, versioned and date-scoped: "Federal — 2018 Farm Bill", "Federal — Section 781 (draft)", "FLEX acquirer pre-regulatory posture", "Visa prohibited products", a state regime. Today's COA Validity Rules becomes simply the first policy in the list — nothing about it changes; it stops being the only one. Each policy has a Qredible-managed default, a per-processor overlay (where allowed), and an effective policy per (policy × processor) — and a product is evaluated under all of them.

ConceptWhat the engine already implements today
Policy (versioned authority rule set)Regime object: authority tier, status (ENACTED / CONTINGENT / MODELED / HISTORICAL), version, effective dates, rules-as-data
Qredible default per policyThe regime's rule set + the corpus dispositions it inherits
Per-processor overlayThe regime overrides block (per-compound: VIOL / THRESHOLD / OK / REVIEW) + per-company overlay config rows (already shipped)
Effective policyComputed default + overlay, per processor — same merge idea as today
Which policies apply to a processorActive-framework selection (global default → per-company override) + preview frameworks — already shipped
One deliberate limit — a feature, not a gap: a processor can overlay policies that express their own posture (their acquirer overlay, their threshold parameters) and can choose which policy is their primary lens. A processor cannot edit a federal statutory policy. Federal verdicts are computed from the statute's own predicates, never configured — an enacted policy version is immutable, and letting a customer soften a federal rule is exactly the liability the engine's asymmetry rule exists to prevent. On non-editable policies processors get full visibility of the effective values plus "Request a change" — the same request flow the COA Validity Rules use today, scoped per policy.

Q2 — What does the Disposition column look like with multiple authorities?

One primary chip (continuity with today), the full picture one hover away, and a portfolio-level lens switch.

  1. The column keeps a single primary chip — the verdict under the viewer's primary lens (their selected active framework). For every current user this is the legacy Farm Bill policy, so on day one the column looks identical to today. Small per-authority dots next to the chip show at a glance that other verdicts exist and whether any disagree.
  2. Hover/click opens the authority breakdown — one row per applicable policy: verdict, the triggering rule with observed value vs threshold (the arithmetic shown), and the status qualifier. A MODELED acquirer verdict always carries "acquirer risk posture — not a determination of federal law"; that sentence travels on the verdict object itself, so no screen can drop it.
  3. A "Lens" selector in the table toolbar re-renders the column under any applicable policy, plus a synthetic "Effective (most restrictive)" lens showing the worst verdict across authorities with a "driven by" tag. Switching lens never recomputes anything — every policy's verdict is already computed and stored on every evaluation pass; the lens only chooses which one is primary on screen. That is why the lens is instant, and why "what does this look like under §781 in December" is a click, not a batch job.
Who picks what: Processors pick their primary lens, may enable preview policies, and submit per-policy change requests for their overlays. Merchants do not pick — the policies that apply to a merchant resolve from their processor relationships and jurisdiction; they see the breakdown (with qualifiers) as a remediation roadmap but cannot choose to be judged by fewer authorities. Qredible super-admins author policies, approve versions, and must run an impact preview before anything activates.

Why this is low-risk to adopt

  • Day-one continuity: with only the legacy policy active, every screen renders exactly what it renders today — one policy in the list, one chip in the column. The multi-policy UI only reveals more when more policies exist.
  • Nothing invents engine behavior: every element binds to an output that already exists and is tested — per-policy verdicts with qualifiers, the most-restrictive effective verdict with attribution, posture diffs, framework selection, and the request-flow precedent.
  • Same kill switch: the UI ships dark behind the same fail-closed configuration flag as the rest of the compliance engine.
  • Sequencing: this design does not gate the September FLEX deliverable (the offboarding export is the FLEX-facing surface and is already built); the UI build queues behind the MyCOA/extraction priority. The first slice worth pulling forward is the disposition-column popover.
