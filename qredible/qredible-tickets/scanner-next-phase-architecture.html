Don't build a new engine. Give the existing one more context — and more ways to act on it.

Today's scanner is excellent at one question: "is this required disclosure present on the page?" The next phase teaches it to reason about who the merchant is, what it sells, and what happens when a customer acts — without throwing away the fast, reliable engine we already run.

Stage one
Where we are today
What the scanner supports now, and exactly where it hits a wall.
What the scanner supports now

A two-tier keyword engine — fast, reliable, deterministic

Every check today asks a presence/absence question over the text of a page: is this on or off? present or missing? That is the right tool for statutory disclosures, and it runs quickly and cheaply across many merchants. Which checks run is configuration per merchant profile, not code — the policy-first foundation the next phase builds on.

Tier 1

Compliance checks — pure keyword / pattern

match( page text ) → present / absent → compliant or deficiency
  • Required-disclosure presence (e.g. license footer, FDA disclaimer, privacy policy)
  • Prohibited-language detection (e.g. guaranteed-approval claims)
  • No AI. Deterministic, auditable, effectively free to run.
Tier 2

Violative terms — keyword, then optional AI

keyword hit → optional AI instructions → violative / not
  • A configurable watchlist of terms and phrases
  • AI is already used here to judge borderline matches
  • Still keyword-triggered — it only looks where a term fires

The important takeaway

The AI execution path already exists for violative terms, and check selection is already config-driven. The next phase is an extension of proven foundations, not a rebuild.

Where it breaks

Three things the engine cannot see

Newer checks are more complex than presence/absence. They fail for one of three reasons — and naming them precisely is the whole design.

Context blindness

Who the merchant is

HAS · the text of the page
LACKS · the merchant's locations, licenses, declared category
A single-state lender gets flagged for a missing multi-state disclosure it never needed.
Single-signal

Several facts, reasoned together

HAS · one string match per check
LACKS · "required only if A and B and not C"
Multi-condition logic can't be a single keyword. It needs a reasoner.
Surface blindness

What it sells & what happens when you act

HAS · one page of text
LACKS · product structure, page interaction, on-page controls
"Is a consent step actually required at checkout?" is unanswerable from text alone.
The emblem case

The single-state lender false positive

A lender operating in one state only was flagged violative for not publishing a multi-state served-states list. It correctly named its single state and was fully compliant — the keyword matcher simply had no idea which state(s) the merchant serves, so it expected a list that didn't apply. Pure keyword logic can't fix this; the check needs the merchant's own facts.

The backlog it creates

The complex checks stuck in manual review

Because the engine can't run them reliably, the most complex checks ship as Analyst Review — a human examines each merchant by hand. That is accurate but slow and doesn't scale. The next phase is about moving these from manual to automated, safely.

The proposal · part 1

The extended check engine — a detection_mode dispatch

One engine, one config model, one results view — unchanged. We make each check's execution mode explicit, and the engine dispatches to the right executor. Existing checks stay in KEYWORD mode and behave exactly as today. Complexity is opt-in, per check.

Why this is the unifying move: a "complex check" is no longer special code. It becomes a definition with a mode, an instruction template, a trigger, and a list of context tokens. Authoring a contextual check becomes a content task for the compliance team; engineering builds each executor once. That is policy-first, realized for complex checks.

The vision, made concrete · end to end

A context-aware AI check, running start to finish

The same single-state-lender case that produces a false positive today, running cleanly in AI mode in the final-state engine. Example values are illustrative.

1

Trigger gate cost & accuracy control

A cheap keyword pre-filter decides whether to invoke the model at all.
trigger: ["available in", "residents of", "we serve", "not available in"]
no match → skip · no model call · match on the terms page → proceed ✓

This is what makes "AI across many sites" affordable: the model runs only where the topic plausibly appears.

2

Resolve merchant context

The resolver pulls the facts (cached) — the thing the old engine never had.
servedStates: one state license: state-level flag: single-state footprint
3

Render tokens into the instruction

The authored template (left) becomes the resolved prompt (right): tokens → values.
Authored instruction (content)
This merchant operates in: {{served_states}}. A multi-state service-area disclosure is required ONLY when more than one state is served. If exactly one state is served, the requirement does not apply → compliant. Otherwise, check for an explicit served / excluded-states list. Return a verdict and a one-sentence rationale.
Resolved prompt (sent to model)
This merchant operates in: [one state]. A multi-state service-area disclosure is required ONLY when more than one state is served. If exactly one state is served, the requirement does not apply → compliant. Otherwise, check for an explicit served / excluded-states list. Return a verdict and a one-sentence rationale.
4

AI verdict (structured)

Forced structured output; the verdict carries its reasoning. Confidence value is illustrative.
{ "isCompliant": true, "confidence": high, "rationale": "Merchant serves a single state; the multi-state disclosure requirement does not apply.", "evidence": "Footer names the single state of operation." }
Confidence
lowhigh ✓

The rationale is saved with the finding, so a reviewer reads why, not just what — the same interpret-it-for-the-customer quality leading risk reports are known for.

5

Confidence routing — how manual checks migrate without an accuracy cliff

No hard cutover. A check can be AI-assisted with an analyst fallback during a transition window.
high
High confidence → automated finding. Our case resolves compliant automatically. The old false positive is gone.
low
Low confidence → Analyst Review, pre-filled with the AI rationale and evidence. The analyst starts from a draft, not a blank page.
The vision · flexible AND scalable

Built to run across many merchants

The architecture is only worth it if the economics work. Each capability has a distinct scaling profile; the levers below are in priority order of impact.

AI cost controls

1

Trigger-gating

No model call unless a cheap keyword pre-filter fires. Most checks on most pages cost nothing.

2

Page-scoping

Send the relevant page(s), not the whole site. Smaller, cheaper, and more accurate at once.

3

Context caching

One merchant's many AI checks share the same resolved context — gathered once, reused for the rest.

4

Tiered models

A fast model for routine classification; escalate to a stronger model only when a verdict is uncertain.

5

Result caching

Unchanged pages on re-scan reuse their prior verdict instead of paying again.

Behavioral throughput & resilience

⧉

Isolated worker pool

Browser-driven checks are slow and heavy, so they run in a separate, independently-scaled pool that never starves the fast text scans.

⟳

Cadence, not every scan

Run interactive checks on onboarding, on detected site change, and on a schedule — the biggest throughput lever.

Graceful degradation — the key to running everywhere
Behavioral check→ fail → On-page read→ fail → Text proxy→ fail → Analyst Review

A site that blocks an interactive check falls back to reading its page, then to a text proxy, then to a human. No check ever crashes a scan; reviewers only see what truly could not be automated.

Why it stays flexible

Every knob — mode, instructions, trigger, page-scope, tokens — lives on the check definition, not in code. Adding a new vertical means publishing a profile that enables a set of checks and supplies their instructions. Engineering builds each executor once; the compliance team grows coverage as content.

Ordered by leverage-per-effort

Everything here is additive

Nothing in the engine running today changes behavior. Today's keyword checks keep running exactly as they do. The new capability is opt-in, per check, through configuration — which is precisely what keeps the scanner flexible and scalable as new verticals are published rather than coded.
