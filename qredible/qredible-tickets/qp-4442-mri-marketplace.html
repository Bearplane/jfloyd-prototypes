Why "not applicable" has to be its own state. The live FDA card's empty copy reads "Daily-ingested FDA databases contain no records matched to this merchant." For a lender that sentence is not merely useless — it reads as a clean bill of health from a regulator that was never going to have a record. NOT_APPLICABLE renders no card, contributes nothing to the Legal score, and is visible only in the Sources tab (screen 2) so nobody thinks the check silently vanished.
Scoring note carried from the spec. CFPB complaint volume scales with a lender's book size, not its misconduct, so the Legal contribution is banded (0 / 1–9 / 10–49 / 50–199 / 200+), and the discriminating terms are untimely responses and monetary-relief rate, not raw count. The numbers above are illustrative only — bands need calibrating against a real lender cohort before any of this reaches a customer report.

Three tiers, and the panel writes the bottom two. 1 — Qredible sets the industry default in Global Settings (screen 4): on / available / add-on / not applicable / coming soon. 2 — the processor sets a standing rule for a whole industry ("on for all my Online Lending merchants, including future ones") via the checkbox above. 3 — the processor overrides one merchant with the toggles themselves. Most specific wins: merchant beats rule beats industry default. Not applicable is the one thing a processor cannot lift — it means the source has no jurisdiction over that industry, so enabling it would spend API calls to guarantee zero results and put a misleading empty card back in the report.
Precedence, made visible. Each row's sub-label states why it is in its current state — "Industry default", "on by your Online Lending rule", "Turned off for this merchant", "Add-on · not in plan", "Not applicable to this industry". That string is the resolver's own provenance field rendered back to the user, so support can answer "why isn't this pulling?" without a database query. A per-merchant toggle or a purchase is never silently overwritten when the industry profile or a processor rule is recomputed.
A standing rule is not a bulk edit — that distinction is the whole point. Selecting merchants in the We-Monitor bulk bar and toggling writes N rows once; a merchant onboarded next month inherits nothing. The rule is evaluated at materialisation time, so it reaches merchants that do not exist yet — including the Flex merchant whose industry Q-Recon only works out after its first scan.

These cells are a proposal, not a decision. CFPB is on for the six financial-services verticals because CFPB only accepts complaints about consumer financial products; FDA is on for the ingestible/product verticals; COA/lab follows the master file's own 8-vertical COA column. Every cell needs compliance sign-off before seeding — the grid is the artefact that makes that review possible in one pass instead of thirty-four.
This grid is tier 1 only. It is what Qredible sets, and it is the same for every processor. A processor never edits this screen — they layer a standing rule for one of their industries (screen 3's checkbox) or a per-merchant override (screen 3's toggles) on top of it. The two states a processor cannot move are Not applicable and Coming soon; Available exists precisely so Qredible can say "this source is meaningful here but we are not turning it on for everyone" and let each processor decide.
Where this lives in the data model. The grid is not a new industry-keyed table. Each row is the mriSources[] field of that industry's policy document; saving materialises per-company rows that the Middleware cron can join set-wise. Processor rules materialise into the same per-company rows, tagged with their own provenance so a later recompute cannot clobber a per-merchant choice. That keeps the compliance engine policy-first — rules as data read by the deterministic resolver that already exists — while still giving the nightly cron a plain indexed table to filter on.

Most specific wins. Purchases sit alongside tier 3 — buying an add-on is a per-merchant fact, and like a manual toggle it is never overwritten by a tier-1 or tier-2 recompute.

Two processors, one merchant. A merchant monitored by two processors can have two different answers for the same source. The pull stays company-global — it runs if any monitoring processor has it on, so it is fetched once, not twice — while each processor sees only their own resolved state in the UI and only their own entitled sources contribute to the risk aggregate they are shown.

The three things that make this buildable

  • The entitlement substrate already exists. pl_source (with element_identity), pl_feature_new (with subscription_price, addon_price, list_in_addons), pl_feature_source and pl_plan_feature_source_restriction are all in the schema. Free / paid / add-on is a matter of seeding rows and adding price columns to the join edge — not a new billing model. One correction to the earlier design note: the trial-delay columns live on pl_plan_feature_restriction (per feature), not on the source-restriction row, so a per-source trial delay is not free.
  • The factor roll-up already has the seam. The aggregate ignores factors marked inactive, but every factor is currently hardcoded active. Replacing that one literal with the resolver's answer is what makes a turned-off source render as "not screened" instead of "screened clear".
  • The collector pattern already exists. CFPB clones the BBB module shape (search client → fuzzy resolver → processor → one summary row with freshness + fetch-status columns) and the litigation cron shape (find-outdated → per-company producer). It must not clone the FDA pattern, which downloads a global feed and creates a company row for every unmatched firm — against a 17-million-record complaint database that would manufacture tens of thousands of junk merchants.

The one hard dependency

None of the per-industry behaviour can resolve until the platform has a canonical industry key. Today "industry" means three unrelated things that share no foreign key: the six seeded pl_segment rows, a free-text scanner category name, and the company's type of company — which the EDR currently prints under the heading "Industry Type". The Industry Vertical Master's 34 verticals settle what the list should be; seeding them onto pl_segment, and filling the already-built-but-empty MCC↔segment join with the master file's Primary and Possible codes, is the first ticket and it blocks the rest.

Open questions for this review

  • Two lending rows. The master file carries both "Short-Term Consumer Lending /Online Lending" and "On-Line Lending" with the same Primary MCC and the same Possible list but different control sets (10 vs 12). One is presumably meant to subsume the other — which?
  • Slash-separated Primary MCCs. Seven verticals list two Primary codes ("5912 / 5499"). Does a vertical get one primary and the rest possible, or genuinely two co-primaries?
  • Consumer complaint narratives. CFPB publishes consumer-written narrative text. The proposal stores it but shows it only to operators, never in a merchant-visible EDR PDF. Confirm.
  • Add-on pricing. Which paid sources, at what price, billed through what — the columns exist, the numbers do not.
  • Kava has no product family. It carries the same 13 controls as Hemp-Derived CBD but nothing in the product taxonomy matches it, so product-driven inference cannot see it.
  • Can a processor rule cover an industry they have no merchants in yet? Allowing it means Westtown can pre-configure Online Lending before onboarding their first lender — useful, but it also means rules accumulate for verticals nobody is monitoring. Recommend allowing it and showing a "0 merchants today" hint rather than blocking.
  • Does an available source still cost anything when off? No pull, so no API cost — but it does occupy a row in every Sources tab. If the catalog grows past ~15 sources the tab needs the "Active only" filter on by default.
